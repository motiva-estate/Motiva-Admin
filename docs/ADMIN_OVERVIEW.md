# Motiva Admin — Complete Overview

_Last updated: July 2026 (mock-backend era)._

This document explains what the Motiva Admin application is, how it is put
together, and what every section does. It is written to be read by a new
engineer or a non-technical stakeholder, so it starts with the big picture
and then walks section-by-section through every screen.

---

## 1. What this app is

Motiva Admin is the **internal control panel** for the Motiva real-estate
brand. It combines two things in one shell:

- A **content management system (CMS)** for everything that appears on the
  public marketing site — projects, properties, gallery, testimonials,
  FAQs, team, company info, contact details, homepage sections, SEO
  metadata.
- A lightweight **CRM** for the sales side — clients (leads and buyers),
  subscriptions/plans they are on, payments they have made, and enquiries
  submitted from the public site.

It also ships user & role management, an audit log, and a settings screen
for system-level actions.

### Current data layer

Right now the admin does **not** talk to a real backend. All reads and
writes go through a **local mock database** in the browser
(`src/lib/api/mock-db.ts`) persisted to `localStorage`. This lets the UI,
routing, roles and workflows be fully exercised without a server.

The mock is fronted by a typed client (`src/lib/api/client.ts`) whose
shape is designed to survive the swap to a real REST/GraphQL backend —
components import `api.clients.list()` etc., not `mockDb.get()`, so a
future NestJS or Lovable Cloud implementation drops in behind the same
interface.

### Tech stack

## 2. Architecture

### 2.1 Routing model

TanStack Router file-based routing under `src/routes/`. Everything
admin-related lives under the `/admin` prefix. The parent layout is
`src/routes/admin.tsx` — it renders the sidebar + header shell and hosts
the auth gate. Child routes (dashboard, clients, projects, etc.) render
into its `<Outlet />`.

Routes use the flat dot-separated convention:

```
admin.tsx                     -> /admin  (layout)
admin.index.tsx               -> /admin  (dashboard)
admin.login.tsx               -> /admin/login
admin.clients.index.tsx       -> /admin/clients
admin.clients.$id.tsx         -> /admin/clients/:id  (edit)
admin.clients.import.tsx      -> /admin/clients/import
admin.projects.new.tsx        -> /admin/projects/new
admin.projects.$id.tsx        -> /admin/projects/:id (edit)
…
```

### 2.2 Auth gate

`src/routes/admin.tsx` is where authentication is enforced:

1. Reads `useAuth()` from `src/lib/auth/context.tsx`.
2. If the session is `ready` and there is no `user`, it redirects to
   `/admin/login?redirect=<current path>`.
3. While loading the session from `localStorage`, it shows a small
   spinner so we don't briefly flash the login page.
4. `/admin/login` is exempt from the gate.

### 2.3 Auth context

`src/lib/auth/context.tsx` is a mock auth layer:

- Session persisted at `localStorage["motiva.admin.session.v1"]`.
- `login(email, password)` accepts **any password** and looks the user
  up by email in the seeded users list. This is intentional for the demo
  shell.
- Exposes `user`, `ready`, `login()`, `logout()`, `hasRole()`,
  `hasAnyRole()`, and a fine-grained `can(action)` gate driven by a
  capabilities table (see Roles & Permissions below).

### 2.4 API client

`src/lib/api/client.ts` exposes one `api` object with a CRUD block per
resource, generated by a `makeCrud("<key>")` helper:

```ts
api.projects.list()
api.projects.get(id)
api.projects.create(patch)
api.projects.update(id, patch)
api.projects.remove(id)
```

Resources with CRUD: `users`, `projects`, `properties`, `gallery`,
`testimonials`, `faqs`, `leadership`, `achievements`, `services`,
`clients`, `subscriptions`, `payments`, `enquiries`, `auditLog`,
`homepageSections`, `seo`.

Non-CRUD helpers:

- `api.payments.byClient(clientId)` — filter helper for the client
  detail sheet.
- `api.getCompany()` / `api.updateCompany(patch)` — singleton company
  record.
- `api.getContact()` / `api.updateContact(patch)` — singleton contact
  record.
- `api.dashboardStats()` — pre-aggregated KPIs for the dashboard.

Every call awaits a tiny artificial latency (`~120ms`) so loading
skeletons and query spinners are visible when developing.

### 2.5 Mock database

`src/lib/api/mock-db.ts`:

- Holds one big `Database` object with arrays for every resource plus
  singletons for company and contact.
- Persisted at `localStorage["motiva.admin.db.v5"]` (bumped whenever the
  seed shape changes).
- `mockDb.get()` reads and lazily seeds if the store is empty or a schema
  bump invalidated it.
- `mockDb.set(db)` writes back.
- `mockDb.uid()` and `mockDb.now()` generate stable IDs and ISO
  timestamps.
- `resetDb()` clears the store — exposed via the Settings danger zone.

### 2.6 Shared UI primitives

Small kit that keeps every admin page consistent:

| Component | File | Purpose |
| --- | --- | --- |
| `PageHeader` | `src/components/admin/PageHeader.tsx` | Title + description + right-aligned actions |
| `EmptyState` | `src/components/admin/EmptyState.tsx` | Icon + heading + description + optional CTA |
| `TableSkeleton`, `ListSkeleton`, `FormSkeleton`, `DetailSkeleton`, `KpiGridSkeleton` | `src/components/admin/Skeletons.tsx` | Loading placeholders used across every page |
| `StatusBadge`, `ClientStatusBadge`, `SubStatusBadge`, `RoleBadge`, `EnquiryStatusBadge` | `src/components/admin/StatusBadges.tsx` | Semantic colored pills |
| `CollectionAdmin<T>` | `src/components/admin/CollectionAdmin.tsx` | Generic list-with-dialog-editor used by simple content types (services, testimonials, FAQs, etc.) |
| `ClientDetailSheet` | `src/components/admin/ClientDetailSheet.tsx` | Right-side slide-in panel for a client, opened from the clients list |
| `AdminSidebar` | `src/components/admin/AdminSidebar.tsx` | Grouped nav filtered by `can(action)` |

## 3. Roles & permissions

Four roles are defined in `src/lib/api/types.ts` and mapped to
capabilities in `src/lib/auth/context.tsx`.

| Action | SUPER_ADMIN | ADMINISTRATOR | CONTENT_EDITOR | VIEWER |
| --- | :-: | :-: | :-: | :-: |
| `content.create` | ✅ | ✅ | ✅ | — |
| `content.edit` | ✅ | ✅ | ✅ | — |
| `content.publish` | ✅ | ✅ | — | — |
| `content.archive` | ✅ | ✅ | — | — |
| `seo.manage` | ✅ | ✅ | — | — |
| `contact.manage` | ✅ | ✅ | — | — |
| `homepage.manage` | ✅ | ✅ | — | — |
| `clients.manage` | ✅ | ✅ | ✅ | — |
| `subscriptions.manage` | ✅ | ✅ | — | — |
| `enquiries.assign` | ✅ | ✅ | ✅ | — |
| `users.manage` | ✅ | — | — | — |
| `audit.view` | ✅ | ✅ | — | — |
| `settings.manage` | ✅ | — | — | — |

The sidebar filters items using each item's `require` action, so a
`VIEWER` sees only the Dashboard, and a `CONTENT_EDITOR` sees Content +
Clients + Enquiries but not Users, Audit, Settings, SEO, Homepage,
Contact, or Subscriptions.

Demo accounts are seeded — pick any email from the Users page on the
login screen; any password works.

## 5. Section-by-section walkthrough

Each section below covers: **route**, **purpose**, **what the user sees**,
and **what they can do**.

### 5.1 Login — `/admin/login`

- File: `src/routes/admin.login.tsx`
- Purpose: sign into the admin.
- Behaviour: any password is accepted; the email must match a seeded
  user. Success stores a session in `localStorage` and redirects to the
  `redirect` search param (or `/admin`).
- Prefills `admin@motivaestate.com` / `demo` so the app is one click away.

### 5.2 Dashboard — `/admin`

- File: `src/routes/admin.index.tsx`
- Data source: `api.dashboardStats()`.
- KPI cards: Active clients, Active subscriptions, Expiring soon (30d),
  New enquiries, Content awaiting review, Published projects, Published
  properties. Each card shows a large value plus a small subtext (e.g.
  drafts count).
- Two lower cards: **Recent activity** (last 8 audit entries) and a
  quick-links / today block.
- Loading: `KpiGridSkeleton` and skeleton list rows while stats resolve.

### 5.3 Content — Projects

- List: `src/routes/admin.projects.index.tsx`
  - Table columns: title, city, status, listing type, featured, updated.
  - Actions: search, "New project" button, row-level edit / delete.
- New: `src/routes/admin.projects.new.tsx` — minimal form (title, city,
  status) then redirects to the full editor.
- Edit: `src/routes/admin.projects.$id.tsx` — extended editor that
  mirrors the public `/projects/$slug` page: tagline, overview,
  property type, listing type (BUY / RENT / OFF_PLAN), availability
  label, bedrooms, bathrooms, size, land size, delivery date, from-price,
  amenities, units, payment plans, neighbourhood (coords + nearby
  places), gallery images.
- Status flow: DRAFT → REVIEW → PUBLISHED → ARCHIVED.

### 5.4 Content — Properties

- List: `src/routes/admin.properties.index.tsx` — same table pattern as
  projects but includes price and beds/baths.
- Edit: `src/routes/admin.properties.$id.tsx` — same extended editor as
  projects (properties reuse the detail-page shape).
- Properties can optionally link to a parent project via `projectId`.

### 5.5 Content — Services

- File: `src/routes/admin.services.index.tsx`
- Rendered by `CollectionAdmin<Service>`: list of cards with a
  New/Edit dialog for title, slug, summary, body, icon, order,
  isPublished.

### 5.6 Content — Gallery

- File: `src/routes/admin.gallery.index.tsx`
- Manages `GalleryItem` rows: image URL, caption, category, order, plus
  optional `projectId` / `propertyId` linkage.

### 5.7 Content — Testimonials

- File: `src/routes/admin.testimonials.index.tsx`
- CollectionAdmin editor for `Testimonial`: author name, title, quote,
  rating, avatar URL, status, optional project link.

### 5.8 Content — FAQs

- File: `src/routes/admin.faqs.index.tsx`
- CollectionAdmin editor for `FAQ`: question, answer, category, order,
  `isPublished`. Seeded with the questions from
  `motiva-beta.vercel.app/faq`.

### 5.9 Content — Team & Milestones

- File: `src/routes/admin.team.index.tsx`
- Two sections in one page:
  - **Leadership** entries (`LeadershipEntry`) — name, role, bio, photo,
    order.
  - **Achievements** / milestones (`Achievement`) — title, description,
    year, order.

### 5.10 Clients — list

- File: `src/routes/admin.clients.index.tsx`
- Search box (name/email/phone), status filter via URL search params.
- Table columns: name, email, phone, status, latest subscription plan,
  assigned project.
- Clicking a **row** opens the slide-in detail sheet by setting
  `?client=<id>` in the URL — deep-linkable and back-button friendly.
- Row-level actions (edit, delete) stop propagation so they don't open
  the sheet.
- Top-right actions: "Import" (wizard) and "New client".

### 5.11 Clients — detail sheet

- File: `src/components/admin/ClientDetailSheet.tsx`
- Opened from the clients list. Right-side shadcn `Sheet` (~420px on
  desktop, full-width on mobile) with scroll inside.
- Sections in order:
  1. **Header** — avatar circle (uploaded photo or initials), full name,
     `ClientStatusBadge`.
  2. **Personal information** — first/last name, email, phone, contact
     address.
  3. **Next of kin** — first/last name, phone, address.
  4. **Subscription** — subscribed project/property tag chips, plan name,
     start → end date (from latest active `Subscription`).
  5. **Payment breakdown** — two stat cards (Total paid, Balance left) +
     chronological payment list. All amounts in Naira (₦) with thousands
     separators.
  6. **Documents** — three rows (ID, utility bill, passport). Each shows
     a file icon and either an open-in-new-tab link or "Not uploaded".
  7. **Terms & signature** — accepted flag, signature name + date, or a
     stub "Capture signature" button.
  8. **Notes** — free-text with whitespace preserved.
  9. **Activity** — merged reverse-chronological timeline (audit log
     entries for this client + subscription and payment events).
- Sticky footer: **Edit client** (links to `/admin/clients/:id`) and
  **Send reminder** (toast stub).

### 5.12 Clients — edit page

- File: `src/routes/admin.clients.$id.tsx`
- Full form for every field on `Client` — the sheet is view-first, this
  page is the write surface.

### 5.13 Clients — import wizard

- File: `src/routes/admin.clients.import.tsx`
- Multi-step CSV upload: paste/upload → Zod validation → preview → commit.
- Marks imported rows with `source: BULK_IMPORT`.

### 5.14 Subscriptions — `/admin/subscriptions`

- File: `src/routes/admin.subscriptions.index.tsx`
- Table of every `Subscription`: client name, plan, status
  (ACTIVE/PENDING/EXPIRED/CANCELLED), start, end, amount, auto-renew.
- Filters by status; row action opens the underlying client sheet.

### 5.15 Enquiries — `/admin/enquiries`

- File: `src/routes/admin.enquiries.index.tsx`
- Inbox view of `Enquiry`. Status pipeline:
  NEW → CONTACTED → QUALIFIED → CONVERTED / LOST.
- Actions: change status, assign to a user, convert to client.

### 5.16 Site — Company

- File: `src/routes/admin.company.index.tsx`
- Single-record editor for `CompanyInfo`: founding year, mission,
  vision, homes delivered, cities served, years experience, happy
  clients.

### 5.17 Site — Contact

- File: `src/routes/admin.contact.index.tsx`
- Editor for `ContactInfo`: primary email/phone, WhatsApp, list of
  offices (label, address, city, phone), social links map.

### 5.18 Site — SEO

- File: `src/routes/admin.seo.index.tsx`
- One row per page key or per project/property. Fields: title (<60ch),
  description (<160ch), og:image URL, canonical URL.

### 5.19 Site — Homepage

- File: `src/routes/admin.homepage.index.tsx`
- Reorder and toggle visibility of homepage sections
  (`HomepageSection[]`) — hero, featured projects, testimonials, etc.

### 5.20 System — Users & Roles

- File: `src/routes/admin.users.index.tsx`
- List of team members. Fields: full name, email, `Role`, active flag,
  2FA enabled, last login. Only `SUPER_ADMIN` sees it.

### 5.21 System — Audit Log

- File: `src/routes/admin.audit.index.tsx`
- Read-only timeline of `AuditLog`: actor, action, entity type + id,
  changes JSON, timestamp. Available to `ADMINISTRATOR` and above.

### 5.22 System — Settings

- File: `src/routes/admin.settings.index.tsx`
- Two cards:
  - **Backend** — informational, points at
    `src/lib/api/client.ts` and shows the eventual base URL env var
    (`VITE_API_BASE_URL`).
  - **Danger zone** — "Reset demo data" wipes the mock DB and reloads.

## 7. Design system notes

- Tokens are defined in `src/styles.css` using Tailwind v4 `@theme`
  variables. All colors are semantic (`bg-background`, `text-foreground`,
  `border-border`, `text-muted-foreground`, `bg-primary`, etc.) — never
  hard-coded hex values in components.
- Status colors are centralised through the `StatusBadge` family so
  green = active/paid, amber = pending/expiring, red = lapsed/overdue is
  consistent everywhere.
- Scrollbars are custom-styled (6px, transparent track, muted thumb) to
  blend with the theme.
- Loading is always a **skeleton** matching the component's real shape,
  never a generic spinner (except the initial auth boot).
- Empty states always render `EmptyState` with an icon + heading +
  description + optional CTA — never a bare "No data".
- Typography uses the `font-display` utility for headings and card
  values; body text uses the default sans stack.

## 8. Local mock DB

Storage key: `motiva.admin.db.v5`.

Seed contents include:

- Users covering all four roles.
- A handful of published + draft projects and properties matching the
  `motiva-beta.vercel.app/projects` catalogue.
- Gallery, testimonials, FAQs, services, team, achievements.
- Company + contact singletons.
- Clients with subscriptions, payments, and audit entries so the detail
  sheet has content out of the box.
- Enquiries in each status.

To reseed: Settings → Danger zone → Reset. To force reseed after
changing the seed shape: bump the `v5` suffix in `mock-db.ts`.

## 9. Swapping to a real backend

The whole point of the client shape is that swapping is a one-file
change:

1. Reimplement each method in `src/lib/api/client.ts` to `fetch()` the
   real endpoint. Keep return shapes identical to the types in
   `types.ts`.
2. Replace the mock `login()` in `src/lib/auth/context.tsx` with a real
   POST to `/auth/login`; store the returned token in memory/HttpOnly
   cookie rather than putting the whole user in `localStorage`.
3. Move file uploads (client documents, gallery images) to a real
   storage backend — currently the UI only stores URLs the user pastes.
4. Emit audit-log entries server-side on writes rather than relying on
   the client to append.
5. Delete `mock-db.ts` and the "Reset demo data" card once the switch is
   permanent.

When targeting Lovable Cloud, the same interface can be backed by
`createServerFn` handlers that talk to Supabase; RLS + `user_roles`
should mirror the capability map in section 3.

## 10. Known limitations / TODOs

- No real persistence — everything lives in the current browser.
- No file uploads; documents and images are URL strings.
- Signature capture on the client sheet is a stub toast.
- No payment CRUD UI — payments are seeded and shown but not editable.
- No email sending; `EmailLog` type exists but nothing writes to it yet.
- Audit-log entries are best-effort and only added by a subset of
  mutations.
- SSO / 2FA are represented on `User` but not wired to any real flow.
- Public-site metadata (og:image, JSON-LD) is not yet driven by the SEO
  screen.
